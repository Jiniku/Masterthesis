\section{Overview}
\label{sec:overview}

\code{quizgen} turns a course textbook into one or more exam papers that
match a professor-specified \emph{blueprint}. The guiding design decision
is the separation of \textbf{generation} from \textbf{selection}: instead
of asking a language model to write ``the exam'' in one shot, the system
first \emph{over-generates} a large, richly tagged \emph{pool} of candidate
questions, and then \emph{selects} an optimal subset that satisfies the
blueprint exactly. This is the \emph{generate-then-select} (or
over-generate-and-rank) pattern.

\paragraph{Why this architecture.}
A single end-to-end prompt couples two concerns that have very different
failure modes. Generation is creative and stochastic; satisfying hard
quantitative constraints (``exactly 10 questions from Chapter~1, a
40/40/20 difficulty split, two non-overlapping versions'') is a
combinatorial optimisation problem that LLMs are poor at and that has an
exact, auditable solution. By decoupling them we get:
\begin{itemize}[nosep,leftmargin=1.4em]
  \item \textbf{Auditability} --- every question traces back to a source
        chunk (\code{source\_ref}); every exam traces back to a blueprint.
  \item \textbf{Exact constraint satisfaction} --- selection is solved with
        a Mixed-Integer Program, not coaxed from a prompt.
  \item \textbf{Reusability} --- one pool yields many exams / versions.
  \item \textbf{Separable evaluation} --- grounding, deduplication, schema
        validation and LLM-as-judge each operate on finished artifacts.
\end{itemize}

Figure~\ref{fig:pipeline} shows the full flow. The stages map one-to-one
onto modules in the \code{quizgen} package (Table~\ref{tab:modules}).

\section{Data model and contracts}
\label{sec:schema}

Every artifact is a Pydantic~v2 model (\mod{schema.py}), so the data
contract is the single source of truth and a JSON~Schema is \emph{exported}
from it rather than hand-written (they cannot drift). The central type is
\code{Question}:

\begin{lstlisting}
class Question(BaseModel):
    id: str                 # uuid4 hex[:12]
    chapter: int            # >= 1
    section: str | None
    qtype: QuestionType     # mcq | true_false | short_answer | cloze
    bloom_level: BloomLevel # remember .. create  (revised Bloom, 2001)
    difficulty: Difficulty  # easy | medium | hard
    stem: str               # >= 10 chars
    options: list[str] | None
    answer: str             # >= 1 char
    explanation: str        # >= 10 chars
    source_ref: str         # chunk id(s) grounding this question
\end{lstlisting}

The three enumerations (\code{QuestionType}, \code{BloomLevel},
\code{Difficulty}) are reused everywhere, so a tag can never be a free-text
typo. \code{source\_ref} is what makes the pipeline auditable: it links a
question back to the exact chunk(s) it was grounded in. A \code{Quiz}
wraps a list of questions plus the \code{blueprint} dict that produced it,
so an assembled exam is self-describing and reproducible.

% =====================================================================
\section{Stage 1 --- Ingestion}
\label{sec:ingest}

\mod{ingest.py} extracts text from the textbook PDF with PyMuPDF, parses
the built-in table of contents into a chapter\,$\to$\,section tree, and
splits each section into overlapping \emph{chunks} of roughly 500--800
tokens. Each \code{Chunk} carries provenance: \code{chunk\_id},
\code{chapter\_num}, \code{section\_label}, page range, and token count.

\paragraph{Offline tokenizer fallback.}
Chunk sizing uses \code{tiktoken}, whose BPE vocabulary is downloaded on
first use. On an air-gapped machine (or behind a restrictive proxy) that
download fails, so \code{\_get\_encoder} transparently falls back to a
\code{\_WordTokenizer} shim that approximates $\sim$1.3 sub-word tokens per
whitespace word --- accurate enough to drive chunk-size targets without a
network. This keeps the whole pipeline runnable offline.

% =====================================================================
\section{Stage 2 --- Vector Index (RAG)}
\label{sec:index}

\mod{index.py} embeds every chunk with a local sentence-transformers model
(\code{all-MiniLM-L6-v2}) and stores the vectors in a persistent ChromaDB
collection with metadata (chapter, section). At generation time, a query
retrieves the top-$k$ most relevant chunks, which become the grounding
\emph{context} for the LLM. This is Retrieval-Augmented Generation: the
model is constrained to write only about what was retrieved, which is what
makes \code{source\_ref} meaningful and keeps questions on-topic and
factual.

ChromaDB was chosen because it runs fully locally, persists to disk, and
supports metadata filtering (so retrieval can be scoped to a specific
chapter). A lightweight word-overlap \code{check\_grounding} heuristic
flags any generated answer whose content words do not sufficiently overlap
the retrieved context.

\section{Stage 3 --- Controlled, grounded generation}
\label{sec:generate}

This is where the pedagogical control lives. Three concerns are kept in
separate, auditable places:

\begin{enumerate}[leftmargin=1.6em,nosep]
  \item \mod{bloom.py} --- \emph{what} to ask for (the cognitive plan).
  \item \mod{generate.py} --- \emph{how} to ask the model for it (prompts).
  \item \mod{llm\_client.py} --- \emph{how to force} valid JSON back.
\end{enumerate}

\subsection{The cognitive plan (\mod{bloom.py})}

\mod{bloom.py} is the single source of truth for prompt-craft. It holds a
natural-language description of each of the six revised-Bloom levels and
each difficulty tier, plus one schema-shaped few-shot example per Bloom
level (\emph{Bloom-aligned prompting}). It then turns a high-level request
into a concrete, ordered list of \code{QuestionSpec} objects that
generation must fulfil exactly.

\paragraph{Balanced planning.}
\code{build\_balanced\_plan(total, \dots)} spreads questions across Bloom
levels and imposes a target difficulty mix. The arithmetic that makes the
counts \emph{exact} is the \textbf{largest-remainder (Hamilton)} method:

\begin{equation}
\text{raw}_k = w_k \cdot N,\quad
\text{floor}_k = \lfloor \text{raw}_k \rfloor,\quad
r = N - \!\sum_k \text{floor}_k ,
\end{equation}
then the $r$ leftover units are handed to the $k$ with the largest
fractional remainders $\text{raw}_k - \text{floor}_k$. This guarantees the
per-level / per-difficulty counts sum to exactly $N$ even when the target
fractions do not divide evenly --- so ``40/40/20 of 12'' is unambiguous.

\subsection{Prompting and tag coercion (\mod{generate.py})}

\code{generate\_controlled\_for\_chapter} batches the specs \emph{by Bloom
level}, so each LLM call carries that level's description and few-shot
example. For each batch it builds a prompt containing: the Bloom guidance,
the difficulty guidance, the few-shot example, the retrieved grounding
passages, and an explicit, numbered \code{\#SPEC} block --- one directive
per requested question:

\begin{lstlisting}[language=]
#SPEC 1 | bloom=apply | difficulty=medium | qtype=mcq
#SPEC 2 | bloom=apply | difficulty=hard   | qtype=short_answer
\end{lstlisting}

\paragraph{Authoritative tagging.}
Models do not perfectly obey the requested cognitive level. Rather than
trust the returned \code{bloom\_level}/\code{difficulty}, the code
\emph{coerces} every returned question to the tag that was requested
(logging any deviation). This guarantees the pool's distribution matches
the plan exactly --- the selection stage can then rely on the tags being
true by construction.

\subsection{Guaranteed-valid JSON (\mod{llm\_client.py})}

\code{LLMClient} wraps any OpenAI-compatible endpoint (GLM, Ollama, vLLM,
OpenAI) --- switching provider is a \code{.env} edit, nothing else. Schema
validity is enforced by \code{chat\_schema}, which selects a strategy from
the \code{STRUCTURED\_OUTPUT\_MODE} setting (Figure~\ref{fig:structured}):

re-validated by Pydantic, so a malformed item is dropped, not emitted.

\section{Stage 4 --- Blueprint and Automated Test Assembly}
\label{sec:assemble}

\subsection{The blueprint (\mod{blueprint.py})}

A \emph{blueprint} is the small YAML file the professor edits. It is
deliberately separate from generation --- it drives \emph{selection}, not
\emph{creation}:

\begin{lstlisting}[language=]
title: "AI-1 Midterm"
total_questions: 20
chapters: { 1: "50%", 2: "30%", 3: "20%" }
difficulty_mix: { easy: 0.4, medium: 0.4, hard: 0.2 }
allowed_qtypes: [mcq, true_false, short_answer, cloze]
versions: 2
selector: mip          # greedy | mip
dedup_similarity: 0.85
\end{lstlisting}

Chapter and difficulty quantities accept integer counts, fractions, or
\code{"NN\%"} strings; \code{Blueprint.resolve()} converts them to exact
integer counts (again via largest-remainder) summing to
\code{total\_questions}, so everything downstream is unambiguous.

\subsection{Test assembly as optimisation (\mod{assemble.py})}

Selection is \emph{Automated Test Assembly} (ATA): choose, from the pool,
the subset(s) of questions that satisfy all blueprint constraints while
maximising overall quality. Two interchangeable selectors sit behind one
\code{Selector} interface (chosen by \code{blueprint.selector}):

\begin{description}[leftmargin=1.4em,style=nextline]
  \item[\code{GreedySelector}] A fast, content-balancing greedy fill.
  Honours per-chapter counts, respects the difficulty marginal in a
  two-pass fill (quota first, then remainder), and skips near-duplicates
  and questions already used in another version. Good baseline; no
  optimality guarantee.
  \item[\code{MIPSelector}] A Mixed-Integer Program (PuLP\,/\,CBC) that
  meets per-chapter \emph{and} difficulty counts exactly, maximises total
  quality, keeps parallel versions disjoint, and forbids near-duplicate
  pairs across versions. This is the exact, auditable selection.
\end{description}

\paragraph{MIP formulation.}
Let $\mathcal{P}$ be the (qtype-filtered) pool, $V$ the set of versions,
and $x_{iv}\in\{0,1\}$ indicate that question $i$ is placed in version
$v$. With per-chapter targets $n_c$, per-difficulty targets $m_d$, a
quality weight $q_i$, and the set $D$ of near-duplicate pairs:

\begin{align}
\max \quad & \sum_{v\in V}\sum_{i\in\mathcal{P}} q_i\, x_{iv}
   &&\text{(maximise total quality)} \label{eq:obj}\\
\text{s.t.}\quad
& \sum_{i:\,\text{chap}(i)=c} x_{iv} = n_c
   && \forall v\in V,\ \forall c \label{eq:chap}\\
& \sum_{i:\,\text{diff}(i)=d} x_{iv} = m_d
   && \forall v\in V,\ \forall d \label{eq:diff}\\
& \sum_{v\in V} x_{iv} \le 1
   && \forall i\in\mathcal{P} \label{eq:disjoint}\\
& \sum_{v\in V} x_{iv} + \sum_{v\in V} x_{jv} \le 1
   && \forall (i,j)\in D \label{eq:dup}
\end{align}

Constraint~\eqref{eq:chap} fixes the per-chapter blueprint counts;
\eqref{eq:diff} fixes the difficulty mix; \eqref{eq:disjoint} makes the
parallel versions \emph{disjoint} (no question reused across versions);
\eqref{eq:dup} forbids any near-duplicate \emph{pair} from appearing
anywhere across the assembled set. The objective~\eqref{eq:obj} ranks
otherwise-feasible selections by a cheap quality proxy
(\code{question\_quality}: rewards substantive explanations, well-formed
4-option MCQs, and the more discriminating Bloom levels).

\paragraph{Graceful infeasibility.}
If the exact program is infeasible for a given pool (e.g.\ the pool lacks
enough \code{hard} questions in some chapter), the solver \emph{relaxes}
the difficulty equalities~\eqref{eq:diff}, records
\code{difficulty\_relaxed} in the diagnostics, and re-solves --- the
per-chapter counts and totals are never silently violated. Capacity
warnings are emitted up-front when the pool is too small.

\section{Stage 4/5 --- Deduplication}
\label{sec:dedup}

Near-duplicate questions waste blueprint slots and make parallel versions
predictable. \mod{similarity.py} provides one API
(\code{find\_near\_duplicate\_pairs}) with two backends:

\begin{itemize}[nosep,leftmargin=1.4em]
  \item \textbf{Token-Jaccard} over the canonical question text
  (stem~+~answer~+~MCQ options) --- dependency-free, always available:
  \[
    \mathrm{sim}(q_1,q_2) = \frac{|T(q_1)\cap T(q_2)|}{|T(q_1)\cup T(q_2)|},
  \]
  where $T(\cdot)$ is the set of lowercased word tokens.
  \item \textbf{Embedding cosine} using the sentence-transformers encoder
  already loaded for RAG, which catches paraphrases the lexical measure
  misses. Cosine similarity is computed on $L_2$-normalised vectors.
\end{itemize}

Pairs scoring at/above a threshold are returned as index pairs.
\mod{dedup.py} drops the later member of each pair (keeping the first
occurrence) \emph{before} assembly; the assembler additionally forbids any
surviving near-duplicate pair across versions
(constraint~\eqref{eq:dup}). The backend degrades gracefully: with no
encoder available it uses the offline token measure automatically.

\section{Stage 5 --- Validation and judging}
\label{sec:validate}

\subsection{Validation report (\mod{validate.py})}

\code{validate\_exam} produces a structured report over four dimensions the
thesis cares about:

\begin{enumerate}[nosep,leftmargin=1.6em]
  \item \textbf{Schema validity} --- every question round-trips through the
        \code{Question} model.
  \item \textbf{Blueprint compliance} --- per-chapter counts, difficulty
        mix, total, and allowed qtypes match the blueprint \emph{exactly}.
  \item \textbf{Grounding coverage} --- share of questions traceable to
        source text (has a \code{source\_ref}; and, when source chunks are
        supplied, the answer's content words overlap the referenced
        passage).
  \item \textbf{Duplicate rate} --- share of questions involved in a
        near-duplicate pair.
\end{enumerate}

The overall gate \code{passed} is true only if no schema-invalid items
exist and (if checked) the blueprint is satisfied. The grounding check
reuses the dependency-free \code{extract\_content\_words} helper in
\mod{textmatch.py}; this helper was split out of \mod{index.py} precisely so
validation does not have to import the heavy vector-index stack.

\subsection{LLM-as-judge (\mod{judge.py}, optional)}

A \emph{separate} model call rates each finished question on four criteria
--- answerability, correctness of the keyed answer, clarity, and Bloom-level
match --- on a 1--5 scale, and flags any item whose \emph{minimum} criterion
falls below a threshold for human review. It is deliberately isolated from
generation: it only reads finished questions and never rewrites them, so
``generate'' and ``judge'' stay cleanly separable. It is opt-in; nothing
else depends on it.

% =====================================================================
\section{Orchestration and offline operation}
\label{sec:pipeline}

\mod{pipeline.py} wires the stages into one runnable flow
(\code{ingest $\to$ index $\to$ generate $\to$ dedup $\to$ assemble $\to$
validate $\to$ judge}); each stage is imported from its own module, so the
orchestrator only sequences and reports. Two design choices make the whole
system runnable with no network --- important for reproducible thesis
experiments:

\begin{itemize}[nosep,leftmargin=1.4em]
  \item \mod{mock\_client.py} (\code{MockLLMClient}) is a drop-in
  \code{LLMClient} replacement that parses the \code{\#SPEC} / \code{\#JUDGE}
  directives and synthesises deterministic, schema-valid questions and
  ratings --- no endpoint required (\code{--mock}).
  \item The index build is best-effort: if embeddings cannot be loaded the
  pipeline logs a warning and generates without RAG, and dedup/validation
  fall back to the token backend.
\end{itemize}

\begin{lstlisting}[language=bash]
# Full pipeline, fully offline:
python -m quizgen.pipeline --chapters 1-3 \
       --blueprint blueprint.yaml --mock --judge
\end{lstlisting}

\paragraph{What ``schema validity'' does and does not guarantee.}
Throughout, structured-output enforcement guarantees the \emph{shape} of
the JSON, never the \emph{truth} of its contents. That is precisely why
grounding (Stage~2/5), tag coercion (Stage~3), exact selection (Stage~4)
and judging (Stage~5) are all separate, mandatory or opt-in checks rather
than assumptions baked into the prompt.

\section{Summary}

\code{quizgen} implements a clean separation between \emph{generating} a
large, tagged, source-grounded pool of candidate questions and
\emph{selecting} blueprint-compliant exams from it via exact optimisation.
RAG keeps questions grounded and traceable; Bloom-aligned prompting plus
authoritative tag coercion give exact pedagogical control; a 0--1 MIP gives
exact, auditable, multi-version assembly; and a layered validation suite
(schema, blueprint, grounding, duplicates, optional LLM-judge) verifies the
result. The system runs end-to-end offline, and swapping the LLM provider
is a one-line configuration change.
